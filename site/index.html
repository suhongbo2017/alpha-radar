二、S1 缺陷详情（会让系统输出错误结论）

D-01 三情景事后择优 → "预测永远准"

现象：Base 预测 1.00B，实际 1.55B（偏 +55%），报告输出 -3.1% / A 级。

根因：report 用 min(|error|) 在 Bear/Base/Bull 中事后挑最接近的来评分。

if best_err is None or abs(e) < abs(best_err):
    best, best_err = p["scenario"], e     # ← 事后择优
err_sum.setdefault(metric, []).append(abs(best_err))

**为什么致命**：预测三个数、事后挑最准的来打分 = 永远准。这个虚高的准确率会传导到仓位决策。
它污染的是整个系统最高价值的产出——"我最不擅长预测什么"。

**修复**：预测能力只对 **Base** 计分；三情景改为独立的"区间命中率"。两者分开看：
- `Base 偏 55% 但落在区间内` = 方向对、中心估计偏
- `Base 偏 3% 却跌出区间` = 自欺（区间画得太窄，实际是运气）

**验证**：正确输出 `+55.0% / D`，并独立报告"落在 Base~Bull 之间，区间内"。

## D-02 预测修订后 v1/v2 混算 → 自动化了后见之明偏误

## D-18 append-only 无任何技术保障 ✅ 已修复

**现象**：`git status` → `fatal: not a git repository`。

**为什么是 S1**：整套系统的全部价值建立在"预测完整性"上，而：
- `predictions.jsonl` 可被任何文本编辑器静默改写
- 铁律 5「旧预测永不覆盖」**没有任何技术保障**，只是君子协定
- 折腾几百行代码改动后没有任何 diff 可回溯
- 两年后当你需要回答"我当初到底预测了什么"，无法证明文件没被动过

**修复**（共三层）：

1. `git init` + 首次提交（`966b6ea`），把 15 条预测、全部脚本、skill 与缺陷登记册固化
2. **写入即固化**（[A1]）：`predict` / `actual` / `decision` 落盘后自动 `git commit`，
   提交信息形如 `ledger(prediction): APH Revenue 2030 Base`
3. **G6 门禁**：持续检验"账本已跟踪且与 HEAD 一致"

  ✓ data/predictions.jsonl 已固化且与 HEAD 一致
  HEAD 中 predictions.jsonl: 15 条

**G6 负路径已验证**：往 `predictions.jsonl` 手工追加一行 →
`✗ 有未固化的改动（记了但没提交）` → `__GATE_FAIL__ G6`。

**保护措施**：自动固化仅在真实账本目录生效；`ALPHA_RADAR_HOME` 指向临时目录（测试）时自动禁用 ——
否则 63 项测试会制造 63 个垃圾 commit。

### 一个重要的区分：predictions 必须 append-only，actuals 可以纠错

| | predictions | actuals |
|---|---|---|
| 性质 | "**当时的判断**" | "**已发生的事实**" |
| 改写含义 | 事后修改历史 → **禁止** | 重复录入是操作失误 → **可纠错** |
| 改数方式 | 必须升版本 v(n+1) | 允许删除重复行，但**必须独立提交留痕** |

> 这个区分是修 D-18 时才想清楚的。之前笼统地说"一切 append-only"，
> 结果把一个操作失误（重复写入）变成了不可修复的历史包袱。
> **正确的原则不是"永不修改"，而是"修改必须可见且可归因"。**

## D-32 autocommit 的 `.strip()` 绑定错误（修 D-18 时引入）

## D-43 赔率定义不统一，跨公司比较失效（S2）

**现象**：`APH_BottomUp_Research.md` 得 APH 赔率 **0.5:1**，
`ITRI_BottomUp_Research.md` 得 ITRI **3.9:1** —— 报告里据此得出"ITRI 是六家中赔率最好"。

**根因**：**两把尺子**。

| 报告 | 上行 | 下行 |
|---|---|---|
| APH | 至分析师目标价 | **倍数压缩**（20x FY2027 EPS） |
| ITRI | 至分析师目标价 | **52 周低点** |

**为什么 52 周低点不能当分母**：它是**已经发生的价格**，不是**基本面下行风险**。
用它当分母，等于假设"最多只跌到最近的低点"——这不是投资假设，是把历史当承诺。

**影响**：换成一致定义（上行 = 情景加权价值涨幅；下行 = 至 Bear 情景跌幅）后：

| 标的 | 旧口径 | 一致口径（5 年） | 一致口径（3 年） |
|---|---:|---:|---:|
| APH | 0.5 : 1 | **0.92 : 1** | **0.01 : 1** |
| ITRI | 3.9 : 1 | **0.91 : 1** | **0.69 : 1** |

**两者几乎相同** —— "ITRI 赔率最好"的结论不成立。

**修复**：定义已写死入 `Alpha_Radar_SKILL.md` §5.3b：

上行 = 情景加权价值 / 现价 − 1
下行 = 1 − Bear 情景价值 / 现价
赔率 = 上行 / 下行

> **这条缺陷的意义超出赔率本身**：它说明**两个"看起来差不多"的口径，
> 可以把结论从"最好"翻成"一般"**。指标定义不统一时，任何横向比较都是无效的。

## D-45 L1 在无 GrossProfit 时静默什么都不做（S2）

**现象**：INTU 的 `[L1] 会计恒等式` 输出了**一个表头，零行**。

## D-46 净债务未扣短期投资（S1）—— 本轮最重要的发现

**根因**：`net_debt = 债务 − 现金及现金等价物`，**未扣除短期投资**。

| 公司 | 短期投资 | 错误净债务 | 正确净债务 |
|---|---:|---:|---:|
| APH | $0.6897B | $14.08B | **$13.39B** |
| INTU | $2.495B | $2.96B | **$0.47B** |
| ITRI | 无 | $0.865B | $0.865B ✓ |

**为什么是 S1**：污染链很长 —— 净债务 → 投入资本 → **ROIC** → **Net Debt/EBITDA** → 杠杆判断。
而且**它已经写进了已提交的 APH 档案**。

**修复**：
1. 新增 `CASH_LIKE_EXTRA`（含 2026+ 新 XBRL tag）并与现金算和
2. 现金组在**同一日期**上可能命中多个 tag（现金 + 短期投资），必须**求和**，
   但同一数字的多个别名不能重复计
3. 抽出 `Facts.balance_sheet()` 作为**引擎与校验器共用的唯一路径**

**验证**：修复后三家公司净债务均与独立报告吻合

**已回滚修复已提交的档案**：APH 档案已更正（见其附录），评分不变（两个受影响项落在同一锚档）。

## D-47 `pctdiff() or 99` 假值零静默关闭检查（S1）

**现象**：capex 口径修正的代码写了，却不生效。

if y0 in am2 and abs(pctdiff(va + am2[y0], vb) or 99) < 1:

当两个值**完全相等**时 `pctdiff` 返回 `0.0`；而 **`0.0` 在 Python 里是假值**，
`0.0 or 99` → **99** → `abs(99) < 1` 为 False → **检查被静默关闭**。

> **完全相等的两个值反而被判为失败** —— 这是最难发现的一类 bug：
> 它只在"应当通过"的分支上出错，且不报错。

**修复**：新增 `close_enough()`，用显式 `is not None` 判断，禁止 `or` 兜底。

## D-50 校验器第三次"测引擎没走的路径"（S1）

# 六、元教训（比单个缺陷更重要）

### 1. 最坏的失败模式不是崩溃，是安静地给错答案

17 个 S1 缺陷里 16 个不报错。它们不抛异常、不崩溃，
只是让报告显示"预测很准"、"误差 96.8%"、"B 级"。

> **一个投资决策系统的首要质量属性不是"能跑"，而是"错了会说出来"。**

### 2. 纪律不能靠自觉，必须变成代码约束

v1.0 把纪律写在文档里（"旧预测永不覆盖"、"先基本面后估值"），
但数据层默认"模型会老实填"。所有 S1/S2 缺陷都是这个假设的产物。

> **让它难以犯错，而不是提醒别犯错。**

### 3. 文档和代码会脱节，而且没有机制发现

D-20 就是这么来的：我先写 SKILL.md §6 描述行为，再（不完整地）改代码。
**G5 门禁第一次运行就抓到 3 处真实漂移。** 现在有机制了。

### 4. 从没红过的门禁等于没验证

第一次跑通 15/15 门禁时，这套门禁其实**未经检验**。
负路径测试（注入故障）才是真正的验证 —— 一个故障被 2 个独立门禁抓到。

### 5. 改代码和验证代码必须分开做

D-19（我自己引入的崩溃）不是测试抓到的，是人工 grep 发现的。
D-25（假测试）说明测试本身也需要被审查。

### 6. 跨进程编排不要假设对方环境和你一样

D-26：我在 git-bash 里，就以为 Herdr 新 tab 也是 bash。结果挂死 300 秒。
**显式探测 > 隐式假设。**

### 7. 扩测试比加功能更值钱

D-31（attribution 追记导致 report 崩溃）是被**新增的 T12 测试**抓到的。
写归因功能时如果只验证 happy path，这个 KeyError 会一直睡到真正做复盘那天才爆 ——
而那正是最不能出错的时候。

### 8. 结论：37 个缺陷里，多数是"跑起来才发现的"

| 怎么发现的 | 缺陷 |
|---|---|
| 静坐读代码看不出来，**必须跑** | D-01, D-02, D-03, D-19, D-26, D-30, D-31, D-32, D-38, D-42 |
| **手算与程序输出对读** | D-34, D-35, D-41 |
| **故障注入测试** | D-39, D-40 |
| 文档与代码对照 | D-20, D-23, D-25 |
| 设计审查就能看出 | D-05, D-06, D-08~D-12, D-43 |

> **可执行的验证不是可选项。** D-26 挂了 300 秒、D-30 静默输出天文数字、
> D-31 直接崩、D-35 把 TTM 算小 10% —— 都只在真正运行时才现身。

### 9. 修好一个缺陷时，往往会把旁边那个旧设计问题照亮

D-18 修完后，才发现"一切 append-only"这个笼统提法是错的：
**预测**（当时的判断）必须不可改写，**实际值**（已发生的事实）重复录入只是操作失误。
两者混为一谈，结果就是把一个可修复的失误变成了历史包袱。

> 由此得出的正确原则不是"永不修改"，而是"**修改必须可见且可归因**"。
> 该原则第一次落地就是 `41396e8` —— 删除重复行，但单独成一个提交并写清原因。

### 10. 新增计算必须与已知正确的参照对账

D-34（平行数组年份错位）与 D-35（YTD 取错时长）都是在**建 APH 档案时**才暴露的。
两个都满足：不报错、输出像正常数字、覆盖多个指标。

> 发现方式只有一个：**把手算结果与程序输出对读**（`alpha_metrics.py` vs `analysis/sec/*.txt`）。
>
> **推论：任何新的指标计算器上线前，都必须先在一个已知答案的样本上跑一次。**
> "看起来合理"不是验证。

### 11. 校验器本身也需要被校验（否则它会给你虚假的安全感）

建 ITRI / INTU 档案时，为数据校验写的代码**自己出了九个缺陷**：

| 缺陷 | 性质 |
|---|---|
| **D-39** | 内部"双路交叉"共享原语 → 注入目标 bug 后仍全绿 |
| D-40 | 内嵌"公司一定在增长"假设 → 对收入下滑的 ITRI 产生假警报 |
| **D-41** | 又犯 D-34（标签与数值来自不同 key） |
| D-42 的检查 | 初版查"数据可用性"、二版用自己的 tag 列表 → 两次都是假绿 |
| **D-47** | `pctdiff(...) or 99` —— 假值零静默关闭检查（相等反而判失败） |
| D-44/D-48 | 财年归属按自然年；候选财年不含未结束财年 |
| D-45 | L1 在无 GrossProfit 时静默什么都不做 |
| D-49 | 把一个指标的性质（收入单调）泛化到 NI/OCF |
| **D-50** | **第三次**"测引擎没走的路径"（调 latest() 而引擎用 latest_common()+求和） |

> **一个永远绿的校验器，比没有校验器更危险** —— 你会因为"有校验"而放心使用错数。
>
> 两条必须执行的规则：
> 1. **要么用完全独立的源，要么明确标注"不独立"。** 共享原语的交叉验证是自欺。
> 2. **校验器必须做故障注入测试**：把它声称能抓的 bug 真的注入一次，确认它变红。
>    没红过的校验器 = 未验证。
> 3. **校验器与被校验对象必须共用"路径"，只在"数值"上独立。**
>    路径不同 → 假绿（D-50）；数值不独立 → 同样假绿（D-39）。
>    两个方向都要防。

### 12. 错误会跨档案传播

D-46（净债务口径）**同时污染了 APH 和 INTU 两份档案**，而且第一份已经提交。
如果不是在第二份上跑了更严的校验，这个错误会一直留在已完成的档案里。

> **每建一份新档案，都必须重跑全部旧档案的校验。**
> 单份档案的校验只能证明"这一份自洽"，不能证明"所有档案都用了同一口径"。
> 这就是 G7 用 `--all` 而不是单公司的原因。

### 13. 外部交叉的覆盖面 = 你能抓到的错误面

D-53（MSFT 的 TTM 财年边界错误）之所以长期静默，是因为外部交叉只覆盖了
revenue/ni/ocf —— **capex 和 FCF 不在范围内**。把它们加进去后，
同一个错误立刻被 **14 条检查**同时抓到。

> **没纳入交叉的字段，就是盲区。** 交叉验证的覆盖面决定了它的上限。

### 14. 第三方口径本身也不统一

对 MSFT 的债务：我们算 **有息 + 融资租赁 = $106.89B**；
Yahoo 算 **有息 + 经营租赁非流动 = $56.83B**（**反而计经营租赁、不计融资租赁**）。

> 既然第三方口径不统一，交叉校验的目标就不是"**相等**"，而是"**能解释差异**"。
> 校验器已改为：逐个尝试候选调整项 → 能精确对上是 DEFINITIONAL（口径），否则才 MISMATCH。
> 实测所有对账都精确到小数点后三位（如 CRM：8.331+0.586 = 8.917 ✓）。

### 15. 指标定义不统一时，横向比较无效

D-43：两个"看起来差不多"的赔率口径（"倍数压缩" vs "52 周低点"），
把结论从"ITRI 赔率最好"翻成"APH 与 ITRI 几乎相同"。

> 在把任何两个标的放进同一张比较表之前，先确认两边的**分母/口径是同一个东西**。
> 否则那张表只是把两个不同的量并排摆放而已。

方法论

系统的证据等级、估值边界和数据校验口径。

五模块闭环

基本面引擎 → 估值引擎 → 决策引擎 → 预测账本 → 复盘引擎

九条铁律

  1. 先基本面，后估值
  2. 先预测企业价值，再看股价
  3. 股价下跌 ≠ 加仓理由；股价上涨 ≠ 卖出理由
  4. 价格变化与基本面变化必须分开记账
  5. 旧预测永不覆盖（append-only）
  6. 每个数字必须有来源与数据截点
  7. 预测错误必须归因
  8. 投资逻辑失效比股价下跌更值得行动
  9. 目标不是提高预测命中率，而是提高长期风险调整后收益
